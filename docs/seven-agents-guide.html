The seven agents behind CareerGraph

CareerGraph turns a pile of job postings into a live skill graph, then uses seven small, single-purpose agents to move a student from "here's my resume" to "here's exactly what to learn next, and why." Two agents build the graph, four score and rank against it with plain deterministic Python, and one optional agent narrates the results in English. This page walks through each one — its motive, its mechanism, its actual code, and why removing it would break something specific.

Ingestion tier — builds the graph from raw data
Algorithmic tier — pure Python, zero LLM, deterministic
Reasoning tier — optional LLM narration layer
Tier 1

Ingestion agents — build the graph

2 agents · zero LLM · run once per data load

1 · IngestionAgent

pure python backend/app/engine/ingestion/ingestion_agent.py

Motive

Real job-posting exports are messy: blank titles, a salary_max lower than salary_min, a skills_required cell that's just empty. Nothing downstream — not the graph, not any agent — should have to defend itself against malformed rows. IngestionAgent's whole job is to be the one place that absorbs that mess, so every other agent can assume clean input.

Mechanism

It reads a CSV (from a path, an uploaded file, or raw bytes/text — all three are duck-typed through _read_text), checks the header contains the required columns, then validates row by row. A bad row is dropped and logged, never allowed to abort the whole run — one malformed posting shouldn't cost you the other 9,999.

ingestion_agent.py:98–136 — per-row validation
def _validate_row(self, row: dict) -> tuple[dict | None, str | None]:
    title = (row.get("title") or "").strip()
    # ... company, location, type, skills_raw pulled the same way
    if not title:
        return None, "missing title"
    # ...
    skills = self._parse_skills(skills_raw)
    if not skills:
        return None, "skills_required had no usable entries"
    if salary_min is not None and salary_max is not None and salary_min > salary_max:
        return None, "salary_min greater than salary_max"
    # otherwise: build and return the clean record dict

Every drop reason gets collected into an IngestionStats object (rows_read, rows_dropped, drop_reasons) rather than swallowed silently — so an ingestion run is auditable: "9,412 read, 32 dropped, 18 for missing skills, 14 for bad salary range."

worked example Row: skills_required = "Python, python, SQL, " → _parse_skills lowercases for dedup but keeps first-seen casing, drops the trailing empty chunk → result: ["Python", "SQL"]. A duplicate entered in different casing collapses to one skill instead of inflating the posting's skill count.

Why necessary

Without it, NormalizationAgent (or worse, GraphService itself) would need its own ad-hoc validation scattered through graph-write code — and a single bad row from a 10,000-row CSV could crash an entire ingestion job instead of costing one dropped record.

2 · NormalizationAgent

pure python + rapidfuzz backend/app/engine/ingestion/normalization_agent.py

Motive

Job postings describe the same skill a dozen different ways — "ReactJS", "React.js", "React" — and a graph that treats those as three different Skill nodes can't match a student who lists "React" against a job requiring "ReactJS". Every downstream agent (gap analysis, recommendations, market demand) depends on skill names being canonical, or their set-intersection logic silently under-counts matches.

Mechanism — a three-step resolution ladder

  • Exact synonym match — case-insensitive lookup in synonyms.json (e.g. "reactjs" → "React").
  • Fuzzy match — if no synonym hit, rapidfuzz.process.extract scores the raw name against the full O*NET/ESCO taxonomy using WRatio; anything scoring ≥ 90 is accepted as that canonical name. Ties at the same top score are broken alphabetically — deterministic, not "whatever the library iterates first."
  • Unmatched — kept as-is and flagged for manual review, rather than silently discarded.
normalization_agent.py:188–203 — deterministic fuzzy tie-break
def _fuzzy_match(self, raw_name: str) -> str | None:
    matches = process.extract(
        raw_name, self._onet_canonical_names,
        scorer=fuzz.WRatio, score_cutoff=self._fuzzy_threshold, limit=None,
    )
    if not matches: return None
    top_score = max(score for _, score, _ in matches)
    tied = sorted(name for name, score, _ in matches if score == top_score)
    return tied[0]  # alphabetically-first canonical name, not library order

It also derives must vs. nice importance from list position — the first half of a posting's (deduplicated) skill list is "must", the rest is "nice" — and writes everything to Neo4j via GraphService.ingest_job_posting, which is MERGE-based end to end, so re-running the same CSV twice never duplicates a Job or Skill node.

job_id key slug(company)::slug(title) — a documented collision caveat: two distinct postings from the same company with the same title collapse into one Job node. Acceptable at capstone scale; production would add a source row id.
importance rule must_count = max(1, ceil(len(skills) / 2)) — first must_count skills (by original listing order) are "must", the rest "nice".

Why necessary

Skip normalization and RecommendationAgent's Jaccard set-intersection (below) becomes near-useless: "React" and "ReactJS" are different strings, so a perfectly-qualified student would show 0% overlap against a job that happens to spell the skill differently.

Algorithmic agents — score against the live graph

4 agents · pure Python · zero LLM · re-run on every request

3 · SkillGapAgent

deterministic backend/app/engine/algorithmic/skill_gap_agent.py

Motive

Answers the single question a student opens the app to ask: "how ready am I for this specific job, and what exactly is missing?" A flat percentage ("you match 40% of skills") hides the difference between missing one deal-breaking requirement and missing five optional nice-to-haves — this agent weights that difference explicitly instead of treating every skill as equally important.

Mechanism

Required skills are split into must and nice buckets (that label already arrived from ingestion — this agent trusts it, defaulting anything missing to "nice" so unclassified data can never inflate the higher-weighted bucket). Each bucket's match ratio is weighted, then a small proficiency bonus differentiates two students who match an identical skill set but know those skills to different depths.

readiness_score = (must_matched / must_total) × 0.7 + (nice_matched / nice_total) × 0.3 × 100 + proficiency_bonus (capped so total ≤ 100)
skill_gap_agent.py:154–172 — the weighted score, zero-division safe
must_ratio = (must_matched / must_total) if must_total else 0.0
nice_ratio = (nice_matched / nice_total) if nice_total else 0.0
base_score = (must_ratio * MUST_WEIGHT + nice_ratio * NICE_WEIGHT) * 100.0

# proficiency_bonus: matched skills only, scaled 0-10 → up to 2.0 pts each,
# averaged over ALL required skills (not just matched) so it can't dominate
readiness_score = min(base_score + proficiency_bonus, MAX_READINESS_SCORE)
worked example Job needs 4 must-have + 2 nice-to-have skills. Student matches 3/4 must, 1/2 nice, at proficiency 8/10 average on matched skills.
base_score = (3/4 × 0.7 + 1/2 × 0.3) × 100 = (0.525 + 0.15) × 100 = 67.5
proficiency_bonus ≈ (4 matched × 0.8 × 2.0) / 6 required ≈ 1.07
→ readiness_score ≈ 68.6 — a student who knows those same 4 skills at proficiency 2/10 instead lands closer to 67.8. Same skill set, different depth, different score.

Why necessary

Without the must/nice split, a job requiring "Python, SQL, Docker, Kubernetes" (all must-have) and one requiring "Python, SQL, Excel, PowerPoint" (Python/SQL must, the rest nice) would treat a student who only knows Python+SQL identically — even though they're much closer to job-ready for the second posting than the first.

4 · RecommendationAgent

deterministic backend/app/engine/algorithmic/recommendation_agent.py

Motive

Ranks all ~9,380 live jobs for a student — not just against the one target role SkillGapAgent evaluates, but across the whole catalog, so the student sees roles they're a good fit for even if they never thought to search for them. A pure exact-match score would miss "close" jobs entirely: someone who knows Python is a real candidate for a Machine Learning role even without that exact skill listed yet.

Mechanism — two blended signals

Exact score is plain Jaccard similarity over skill sets. Partial score gives credit for skills the student doesn't have yet but is one or two LEADS_TO hops away from — BFS outward from the student's known skills, direct edges worth full credit, one-hop-removed worth half.

exact_score = |student ∩ job| / |student ∪ job| partial_score = Σ(depth==1 ? 1.0 : depth==2 ? 0.5 : 0) over unmatched job skills / |job skills| final_score = exact_score × 0.8 + partial_score × 0.2
recommendation_agent.py:107–129 — multi-source BFS for partial credit
def _reachable_within_depth(start_nodes, adjacency, max_depth):
    # BFS from every student skill simultaneously; visited-set makes it
    # cycle-safe and returns the SHORTEST depth to each reachable skill
    depths = {}
    visited = set(start_nodes)
    queue = deque((n, 0) for n in start_nodes)
    while queue:
        node, depth = queue.popleft()
        if depth >= max_depth: continue
        for neighbor in adjacency.get(node, ()):
            if neighbor not in visited:
                visited.add(neighbor); depths[neighbor] = depth + 1
                queue.append((neighbor, depth + 1))
    return depths
worked example Student knows only Python. Graph has Python --LEADS_TO--> Machine Learning. Job requires {Machine Learning, SQL}.
exact_score = |{}| / |{Python, ML, SQL}| = 0 — plain set overlap sees nothing.
partial_score: "Machine Learning" is depth-1 reachable (credit 1.0), "SQL" isn't reachable (credit 0) → 1.0 / 2 = 0.5
→ final_score = 0 × 0.8 + 0.5 × 0.2 = 0.10 — a real, if modest, signal where exact matching alone would have scored this job identically to one requiring nothing the student is remotely close to.

Ties are broken deterministically by job_id ascending — re-running the same request always returns the same order.

Why necessary

Exact-match-only recommendation is brittle at the edges of a student's skill set — it can't tell "one skill away from qualified" from "completely unrelated field," which is exactly the distinction that makes a recommendation feel like guidance rather than a keyword search.

5 · PathFinderAgent

deterministic backend/app/engine/algorithmic/path_finder_agent.py

Motive

A list of missing skills tells a student what they lack; it doesn't tell them what order to learn it in. If "Machine Learning" requires "Python" as a prerequisite, showing both as an unordered todo-list invites a student to start with the harder one. PathFinderAgent turns "missing skills" into an actual ordered roadmap.

Mechanism

LEADS_TO points prerequisite → advanced skill, so building a path to a missing skill means walking backward first (advanced → its prerequisites) to discover the full ancestor chain, then running a topological sort (Kahn's algorithm) forward over just that induced subgraph to get one linear, prerequisite-first order.

Every milestone also gets a weeks_estimate = BASE_WEEKS(2) + max incoming difficulty_jump — a documented v1 proxy, not real historical learning-time data — and any TEACHES courses already resolved by GraphService for that skill.

Why necessary

The cycle-handling detail matters in practice: LEADS_TO edges in this dataset are synthesized by a same-category alphabetical heuristic (ml/graph_build.py), not hand-curated — a naive Kahn's-algorithm implementation would silently hang the moment ingestion produces even one accidental A→B→A loop. The deterministic force-pick guarantees the roadmap endpoint always returns, even against imperfect data.

6 · MarketAgent

deterministic backend/app/engine/algorithmic/market_agent.py

Motive

Backs "what's actually in demand right now" — the Dashboard's market widget and the standalone Market page. Without it, skill recommendations would have no grounding in the labor market: a student would have no way to tell "SQL" is asked for in 61% of postings while "COBOL" appears in 0.3%.

Mechanism

Counts how many distinct jobs require each skill (deduped per-job first, so one job listing a skill twice can't inflate its count), then normalizes against the corpus max — the single most-required skill in this dataset always scores exactly 100, everything else scaled relative to it. That keeps the score meaningful whether the dataset is a 50-job demo seed or the full 10k-row Kaggle export.

demand_score(skill) = (skill's REQUIRES count / max REQUIRES count across all skills) × 100
documented open decision — trend without time-series data The Neo4j schema has no snapshot/history node yet, so a true "demand delta over time" isn't possible in v1. If a caller supplies a prior ingestion snapshot, trend = current_count − previous_count; if not — the common case, only one ingestion run exists — trend is explicitly None, never a fabricated 0 that would read as "flat" instead of "unknown."

Why necessary

This is the only agent with visibility across the entire job catalog rather than one student/job pair — it's what turns "learn Docker" from a generic suggestion into "learn Docker, which shows up in more postings than any other skill in this dataset right now."

Tier 3

Reasoning agent — narrates the numbers

1 agent · optional · pluggable LLM (Claude / OpenAI / Ollama)

7 · ReasoningAgent

llm-backed backend/app/engine/reasoning/reasoning_agent.py

Motive

A readiness score of 68.6% and a list of missing skill names is correct, but it isn't encouraging or explanatory the way a human career coach would be. ReasoningAgent's entire job is to take output the other six agents already computed and put it into plain, supportive English — never to compute or second-guess a number itself.

Mechanism — validated, schema-locked output

Every one of its four methods follows the identical shape: build a prompt that explicitly tells the model "do not invent or change any score," call LLMProvider.complete() with a Pydantic schema, and return whatever validated object comes back untouched. Raw LLM text can never reach a caller — it's forced through GapExplanation, RecommendationNarratives, RoadmapPlan, or MarketSummary first.

Why "necessary" is a stronger claim than it looks

It's the only one of the seven agents explicitly designed to be removable without breaking anything — per system-design.md §9.1: "removing it never breaks the system." EngineOrchestrator (below) wraps every call to it in a try/except and falls back to a real, written-out template sentence, not a blank field. As of this session's docker-compose.yml, LLM_PROVIDER=none in the live environment, so in practice every narrative a user currently sees is the template path — a real, working degradation, not a stub.

The GNN rerank stage — a learned signal bolted onto Agent 4

GNNRecommendationAgent · optional · torch/PyG

GNNRecommendationAgent

torch, optional backend/app/engine/algorithmic/gnn_recommendation_agent.py

Not the 8th agent — a plug-in for Agent 4

System-design.md counts seven agents; this isn't an eighth. It's a swappable inference layer that RecommendationAgent.rank_jobs() can optionally call, using the exact same graceful-degradation contract as the LLM provider: if torch isn't installed, or no trained checkpoint exists on disk, is_available is False and every scoring method returns None instead of raising. Callers must treat None as "fall back to the pure algorithmic path" — never as an error.

a live, working-tree discrepancy worth knowing about docs/current-status.md (dated 2026-08-05) describes this integration as the single biggest missing piece: "EngineOrchestrator has zero references to GNN anywhere." The code on disk right now tells a different story — recommendation_agent.py already accepts a gnn_agent parameter and blends its score in, and orchestrator.py:280–282 passes self.gnn_agent into rank_jobs() on every recommendation request. The doc is stale relative to the working tree (both files show as modified/uncommitted in git status) — the wiring described as "not done" has, in fact, been done since that doc was last written.

Mechanism — retrieve-then-rerank, not score-everything

rank_jobs() always computes the cheap algorithmic scores over every job first (the retrieval stage). Only the top 50 candidates by algorithmic score (GNN_RERANK_POOL_SIZE) get rescored by the model — bounding the expensive inference step instead of running it against a 9,000+ job catalog on every request.

// once a job is in the rerank pool: final_score = exact_score × 0.6 + partial_score × 0.15 + gnn_score × 0.25 // jobs outside the pool keep score_source = "algorithmic"; reranked jobs get score_source = "gnn"

Node embeddings from the graph encoder are computed once per process and cached (_get_z_dict) — without that cache, scoring a 50-job rerank pool would re-run the full GraphSAGE encoder for every single candidate skill pair, the documented difference between milliseconds and minutes.

Conductor

EngineOrchestrator — how the seven agents become one API

backend/app/engine/orchestrator.py

No agent talks to another agent directly. EngineOrchestrator is the single place that fetches graph data (via GraphService), calls the relevant algorithmic agent(s), and then decides whether to ask ReasoningAgent to narrate the result — every narrative method follows the identical four-step shape described in its own docstring:

  1. Run the relevant algorithmic agent(s) — always, deterministically, zero network calls.
  2. Check whether Settings.LLM_PROVIDER is configured.
  3. If yes, call ReasoningAgent. If that raises for any reason — bad key, timeout, malformed output after retries, anything — catch it and fall back to a template.
  4. If no LLM is configured, skip straight to the template. An LLM failure must never propagate as a 500.
orchestrator.py:176–198 — the try-LLM-then-template pattern, in practice
def _gap_narrative(self, gap_result: GapResult) -> dict:
    ra = self._reasoning_agent()
    if ra is not None:
        try:
            explanation = ra.explain_gap({"readiness_score": gap_result.readiness_score, ...})
            return {"explanation": explanation.explanation, ...}
        except Exception:
            logger.warning("ReasoningAgent.explain_gap() failed; falling back to template narrative.")
    return self._template_gap_narrative(gap_result)  # real, written-out copy — never blank

One route worth noting: get_dashboard() deliberately calls zero narrative methods — it's "purely algorithmic," so a broken LLM key can never affect the Dashboard page at all. And compute_gap_analysis() is the single method both POST /gap-analysis and GET /skills/gap call, guaranteeing the two routes always report an identical readiness score for the same (student, job) pair — a real bug class this design closes off by construction rather than by convention.
