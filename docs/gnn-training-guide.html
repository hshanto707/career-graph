The GNN, start to finish: what it is, why it's built this way, and how it actually ends up in a live recommendation

CareerGraph's four algorithmic agents (Jaccard matching, BFS reachability, demand counting) are the system's real, always-on intelligence — deterministic, LLM-free, fully explainable. The GNN is a second, independently-evaluated signal layered on top: a small graph neural network trained to predict which skills a job plausibly requires and which skills plausibly lead to which. This page walks through the whole thing in the order it was actually built — the data, the model, the training run, the honest evaluation against the algorithmic baseline, and finally how a trained checkpoint sitting on disk turns into a real influence on a real API response.

Design decisions — what was chosen, what was rejected, and why

docs/project-roadmap.md Part B · docs/gnn-model.md

Why a GNN at all, and not just more algorithmic agents?

The capstone's scope explicitly calls for a custom-trained AI model, evaluated against the existing hand-tuned baseline — not as a replacement for it, but as a second, independently-assessed signal (docs/project-roadmap.md "Decisions locked in"). A knowledge-graph embedding / GNN link-prediction model was chosen specifically because CareerGraph's data is a graph (Student–Skill–Job–Course–Category, six relationship types already in Neo4j) — a GNN is the natural model family for predicting missing or plausible edges in that structure, as opposed to e.g. a text classifier, which would need to throw away the graph structure to work at all.

Why link prediction, specifically, as the task?

Two edge types were picked as prediction targets: Job –REQUIRES→ Skill and Skill –LEADS_TO→ Skill. Both map directly onto real product questions the system already needs answers to — "does this job plausibly need this skill" and "does knowing this skill plausibly lead toward that one" — so a trained model's output is usable by the exact same downstream consumers (RecommendationAgent, PathFinderAgent) that already consume the algorithmic version of the same signal, rather than needing a new integration point invented just for the model.

Why 2-layer GraphSAGE, not GCN, GAT, or a from-scratch architecture?

Explicitly scoped as "simple and defensible, not a from-scratch novel architecture" (docs/project-roadmap.md Part B item 3) — the thesis contribution is the evaluated integration (a trained model, compared honestly against a real baseline, actually wired into production), not novel architecture research. GraphSAGE was picked over GCN because it naturally supports the heterogeneous, multi-relation graph here (different SAGEConv per edge type via HeteroConv) without requiring a shared adjacency normalization scheme across node types the way vanilla GCN does. GAT (attention-weighted aggregation) was a plausible alternative and is named directly as the concrete next step if richer input features are added later (see §7 and docs/conclusion-future-work.md item 3) — attention becomes more useful once nodes have real features to weight, which they don't yet (next point).

Why learned embedding tables instead of real input features?

No node type in the current schema carries rich numeric features — a Skill node is just a name and a category string, not e.g. a text embedding of a skill description. Rather than block the whole pipeline on building a feature-extraction step first, each node type gets a learned nn.Embedding table as its input (§4) — the standard fallback when no better features exist, and a known, explicitly identified limitation (not an oversight) discussed honestly in the results section.

Why is the algorithmic baseline not a strawman?

The comparison baseline (ml/baseline.py) doesn't reimplement a simplified version of the algorithmic logic for the sake of the comparison — it directly imports and reuses RecommendationAgent's actual Jaccard-similarity and depth-1/2 LEADS_TO-reachability functions, the exact same code a real student's request runs through. This was a deliberate methodological choice: a favorable GNN result against a weakened baseline would prove nothing; a result against the system's real production logic is the only comparison worth reporting.

Building the graph — from CSVs to a plain-Python graph object

ml/graph_build.py

No live Neo4j connection is used for training — build_synthetic_career_graph() re-runs the exact same IngestionAgent → NormalizationAgent pipeline the real backend uses, but against FakeGraphService (the same in-memory test double the backend's own test suite uses) instead of a live Bolt connection. This means the exported graph is faithful to what real ingestion would produce — same synonym matching, same rapidfuzz fuzzy-matching threshold, same flag-for-review fallback — while remaining fully torch-free and unit-testable in any environment.

Deliberately zero torch dependency here

This module never imports torch — it only builds plain Python data structures (RawGraph: node id lists + (src_id, dst_id) edge pairs per relation). That's what lets ml/tests/test_graph_build.py run node/edge-count and determinism checks in any environment, including the plain backend test suite with no ML stack installed at all — the heavy torch-dependent tests live in a separate file that auto-skips when torch is missing (§6).

The one piece with no real data source at all: LEADS_TO

Nothing in the ingestion pipeline — real or synthetic — ever populates Skill –LEADS_TO→ Skill edges; no "skill A is a prerequisite of skill B" data source exists yet (docs/data-sources.md). For the GNN to have a second link-prediction task at all, this module synthesizes a small, clearly-labeled placeholder: within each O*NET skill category, skills are sorted alphabetically and chained.

graph_build.py:87–103 — the synthetic LEADS_TO heuristic, in full
def _synthesize_leads_to(
    skill_categories: dict[str, str | None],
) -> list[tuple[str, str]]:
    by_category: dict[str, list[str]] = {}
    for skill_name, category in skill_categories.items():
        if not category:
            continue
        by_category.setdefault(category, []).append(skill_name)

    edges = []
    for category in sorted(by_category):
        names = sorted(by_category[category])
        for a, b in zip(names, names[1:]):
            edges.append((a, b))  # skill[i] -[:LEADS_TO]-> skill[i+1], alphabetically
    return edges
why this matters for reading the results honestly Because this heuristic is deterministic and fully known, a baseline that "reconstructs" it (by checking depth-1/2 reachability over the very edges this function produced) isn't demonstrating skill at prerequisite prediction — it's just replaying a known rule. This is exactly why the LEADS_TO results in §7 need the caveat they get.

Train / validation / test split, and negative sampling

ml/split.py · pure Python, no torch

Edge-level split, not node-level — and why that distinction matters

split_edges() partitions each target relation's real ("positive") edges into disjoint train/val/test sets (default 80/10/10, seeded). This is deliberately edge-level: every node can still appear in multiple splits (a Job node might have some of its REQUIRES edges in train and others in test), but no single edge is ever double-counted across splits. EdgeSplit.is_disjoint() is asserted in train_gnn.py immediately after every split, and independently unit-tested in ml/tests/test_split.py.

split.py:26–31 — the disjointness guarantee, checked not just assumed
def is_disjoint(self) -> bool:
    t, v, te = set(self.train), set(self.val), set(self.test)
    return not (t & v) and not (t & te) and not (v & te)

Leakage-safe: held-out edges never enter the encoder's input graph

This is the detail that makes the split more than a formality. train_gnn.py's build_training_graph() only feeds train-split positive edges (for the two target relations) into message passing — validation and test positives are excluded from the graph the encoder actually sees, not just excluded from the loss function. A model that could "see" a test edge while computing node embeddings, even without being directly trained on it, would have an unfair information advantage at evaluation time; this design closes that off entirely.

Negative sampling — rejecting against the full edge set, not just train

sample_negative_edges() draws random (src, dst) pairs and rejects any pair that's a real edge — checked against train + val + test positives combined, never just train. This matters: if negatives were only checked against train positives, a "negative" sampled for the validation set could secretly be a real held-out test edge, silently corrupting the evaluation.

max_attempts = num_samples * 50 + 1000 // bounded rejection sampling — degrades to fewer-than-requested negatives // rather than looping forever on a graph too dense to find enough negatives

Reproducibility

Every stochastic step — the shuffle before splitting, negative sampling, model weight initialization (§5) — takes an explicit seed parameter, and seed=42 is used consistently throughout ml/. The checkpoint and evaluation report were independently re-run on a later date and reproduced the earlier numbers at noise-level precision (§7) — this is checked, not assumed.

Model architecture — layer by layer

ml/model.py

Encoder: 2-layer heterogeneous GraphSAGE

Every node type gets its own learned embedding table (nn.Embedding) as input — there are no real input features in the schema yet (§ Design decisions). Two HeteroConv layers follow, each wrapping one SAGEConv per message-passing edge type (every real relation, plus a synthetic reverse edge for each, so information flows both directions — e.g. a Skill node also learns from the Jobs that require it, not just the reverse).

model.py:22–58 — HeteroSAGEEncoder (abridged)
class HeteroSAGEEncoder(nn.Module):
    def __init__(self, node_types, message_passing_edge_types,
                 num_nodes_per_type, hidden_channels=64, out_channels=32):
        self.embeddings = nn.ModuleDict({
            nt: nn.Embedding(num_nodes_per_type[nt], hidden_channels)
            for nt in node_types
        })

        def build_conv(out_dim):
            return HeteroConv({
                edge_type: SAGEConv((-1, -1), out_dim)
                for edge_type in message_passing_edge_types
            }, aggr="mean")

        self.conv1 = build_conv(hidden_channels)  # 64-dim hidden layer
        self.conv2 = build_conv(out_channels)   # 32-dim output embedding

    def forward(self, x_dict_placeholder, edge_index_dict):
        x_dict = {nt: self.embeddings[nt](torch.arange(...)) for nt in self.node_types}
        x_dict = self.conv1(x_dict, edge_index_dict)
        x_dict = {k: F.relu(v) for k, v in x_dict.items()}
        x_dict = self.conv2(x_dict, edge_index_dict)
        return x_dict  # final 32-dim embedding per node

Why 2 layers, specifically: each SAGEConv layer lets a node aggregate information from its direct neighbors; stacking two means a node's final embedding reflects its 2-hop neighborhood (neighbors of neighbors) — e.g. a Skill's embedding is shaped by the Jobs that require it, and by whatever those jobs' other required skills are shaped by, one hop further out. This is deep enough to capture meaningful graph structure without the over-smoothing risk deeper GNNs are known for on small graphs.

Decoder: dot product, not an MLP

model.py:60–65 — the entire decoder
class DotProductDecoder(nn.Module):
    def forward(self, z_src, z_dst) -> torch.Tensor:
        return (z_src * z_dst).sum(dim=-1)  # score(u, v) = z_u . z_v, a logit

Two embeddings that are "similar" in the learned 32-dimensional space produce a high dot product — the simplest possible scoring function, and the standard choice for link prediction unless there's a specific reason to need an MLP's extra expressiveness. Logits at training time (for numerically stable BCEWithLogitsLoss), passed through a sigmoid at inference to become a 0–1 plausibility score (§8).

LinkPredictor — the full assembled model, and what gets checkpointed

Wraps the encoder + decoder together, and stores its own constructor arguments as self.config — saved into every checkpoint alongside the weights, so a checkpoint can always be loaded into a freshly-constructed model of the exact same shape without hand-tracking hyperparameters separately. Loading a checkpoint into a differently-shaped model (e.g. after an architecture change) fails loudly with a clear error rather than silently loading garbage weights — a specific, tested edge case (ml/tests/test_gnn_pipeline_requires_torch.py).

Training loop

ml/train_gnn.py

Loss: binary cross-entropy, summed across both target relations

train_gnn.py:172–187 — one epoch, abridged
for epoch in range(1, epochs + 1):
    model.train()
    optimizer.zero_grad()
    z_dict = model.encode(edge_index_dict)  # one encoder pass for the whole epoch

    loss = torch.tensor(0.0)
    for edge_type in TARGET_EDGE_TYPES:  # REQUIRES, then LEADS_TO
        edge_label_index, edge_label = supervision[edge_type]["train"]
        logits = model.decode(z_dict, src_type, dst_type, edge_label_index)
        loss = loss + F.binary_cross_entropy_with_logits(logits, edge_label)

    loss.backward()
    optimizer.step()

Each target relation's positive edges are labeled 1, sampled negatives labeled 0 (built once in build_training_graph()), concatenated into one edge_label_index/edge_label pair per relation — both relations' losses are summed into a single scalar the optimizer steps on, so the encoder learns embeddings useful for both tasks jointly, not two separately-trained models.

The full pipeline — graph export, 60-epoch training, checkpointing — runs in ~30 seconds on ordinary CPU hardware, no GPU needed. This is a genuine reproducibility strength worth stating plainly: any examiner can re-run the entire training pipeline live during a defense if asked.

Evaluation methodology

ml/evaluate.py · ml/baseline.py

The three metrics, explained plainly

  • AUC-ROC — across every positive/negative score pair, how often does the model rank the real edge above the fake one? 0.5 = random guessing, 1.0 = perfect separation.
  • Hits@10 — for each real edge, rank it against all the sampled negatives by score; Hits@10 is the fraction of real edges that land in the top 10. Much stricter than AUC-ROC when the negative pool is large (here, 5,429 negatives per REQUIRES edge).
  • MRR (Mean Reciprocal Rank) — the average of 1 / rank across all real edges; rewards ranking a true edge near the top even when it doesn't crack the top 10, unlike Hits@10's all-or-nothing cutoff.
evaluate.py:35–61 — ranking_metrics(), the actual Hits@k / MRR implementation
def ranking_metrics(pos_scores, neg_scores, k=10):
    hits = 0
    reciprocal_ranks = []
    sorted_neg = sorted(neg_scores, reverse=True)
    for p in pos_scores:
        rank = 1 + sum(1 for n in sorted_neg if n > p)
        reciprocal_ranks.append(1.0 / rank)
        if rank <= k: hits += 1
    return {"hits_at_k": hits / len(pos_scores), "mrr": sum(reciprocal_ranks) / len(reciprocal_ranks)}

The correctness requirement: identical test edges for both models

evaluate.py's main() builds one splits object via prepare_splits(), then passes that same object, unmodified, to both evaluate_gnn() and evaluate_baseline(). Neither function is allowed to construct its own split — a difference in the resulting metrics can therefore only reflect a difference between the models, never a difference in which edges happened to be held out for each. This is the single most important methodological guarantee in the whole evaluation, and it's structural (the same object is passed in), not just a stated intention.

The baseline, precisely: what it is and isn't

Built fresh from only the train-split edges (never val/test — the baseline must not see held-out edges any more than the GNN's message-passing graph does), via two functions directly imported from the live production code:

REQUIRES baseline build_requires_baseline() — job-to-job Jaccard similarity: score(job, skill) = the best skill-set overlap between this job and any other training-set job known to require that skill. Reuses RecommendationAgent's exact exact_score formula.
LEADS_TO baseline build_leads_to_baseline() — depth-1/2 reachability over train-split LEADS_TO edges, reusing RecommendationAgent's own DEPTH1_CREDIT/DEPTH2_CREDIT constants and BFS logic directly, not a reimplementation.

REQUIRES: the baseline wins, on all three metrics

Stated plainly because it's the actual result: on the task the thesis originally hoped the GNN would win, it doesn't. AUC-ROC is close (0.961 baseline vs. 0.937 GNN) but Hits@10/MRR are not (0.116 vs. 0.014, 0.067 vs. 0.012). The most defensible explanation available: positive-edge density is sparse per skill relative to the 5,429-strong negative pool, which favors a heuristic that directly reuses ground-truth co-occurrence structure over an embedding model with no richer input than a learned-from-scratch table per node. This directly contradicts the literature-precedent hope (Node2Vec/GNN approaches closing this gap "at scale," per docs/literature-review.md) — a real, useful negative result, not a hidden one.

LEADS_TO: a genuine learning signal, against weak ground truth

The GNN's AUC-ROC (0.679) meaningfully beats the baseline's coin-flip 0.500 — the model has learned something real about graph-structural similarity between skills. But the baseline's near-perfect Hits@10/MRR (1.000/1.000) isn't a counter-achievement: it's tautological reconstruction of the deterministic alphabetical rule from §1, which the baseline has full visibility into. Neither number should be read as "how good is this at ordering a real learning path," because the ground truth itself is synthetic — this is exactly why §9's live rerank only ever calls score_leads_to, never score_requires.

reproducibility, checked not assumed These numbers were independently re-run on 2026-08-06 from the same source data as an earlier 2026-07-18 run and matched at noise-level precision (0.935→0.937, 0.685→0.679, etc.) — a genuine strength of the evaluation, worth stating as such.

Inference & caching — loading the checkpoint inside the running backend

backend/app/engine/algorithmic/gnn_recommendation_agent.py

Graceful degradation — the exact same contract as the LLM provider

Constructing GNNRecommendationAgent never raises, even with no checkpoint on disk or torch not installed — it just reports is_available = False with a human-readable unavailable_reason. Every scoring method returns None, never an exception, when unavailable or when a candidate node id was never seen at training time. This deliberately mirrors LLMProvider's fallback pattern (backend/app/engine/llm/) — the second implementation of an already-proven pattern, not a new design.

gnn_recommendation_agent.py:69–96 — load-or-degrade, abridged
def _load(self) -> None:
    if not self._checkpoint_path.exists():
        self._unavailable_reason = f"no checkpoint found at {self._checkpoint_path}"
        return
    try:
        import torch
    except ImportError:
        self._unavailable_reason = "torch is not installed (see ml/requirements.txt)"
        return
    try:
        checkpoint = torch.load(self._checkpoint_path, weights_only=False)
        model = LinkPredictor(**checkpoint["config"])
        model.load_state_dict(checkpoint["model_state_dict"])
        model.eval()
        self._model = model
    except Exception as exc:
        self._model = None  # any load failure degrades, never crashes construction
        self._unavailable_reason = f"failed to load checkpoint: {exc}"

Two layers of caching — the difference between milliseconds and minutes

Encoder output, per agent instance: _get_z_dict() runs the full GraphSAGE forward pass exactly once and caches the result — without this, scoring a 50-job rerank pool (§9) would rerun the entire encoder for every single candidate skill pair, since each score call was originally recomputing it from scratch.

The agent itself, process-wide: get_default_gnn_agent() is a module-level singleton, not reconstructed per request. EngineOrchestrator is rebuilt fresh on every API call (app/core/deps.py::get_orchestrator) — without a process-wide cache, the checkpoint would reload from disk (a torch.load deserialization) on every single request to any route, not just recommendation requests.

gnn_recommendation_agent.py — the singleton getter, in full
_default_agent: GNNRecommendationAgent | None = None

def get_default_gnn_agent() -> GNNRecommendationAgent:
    global _default_agent
    if _default_agent is None:
        _default_agent = GNNRecommendationAgent()
    return _default_agent

Measured live, after this caching was in place: first request after a cold process start ~0.7s (building the graph + one encoder pass); every request after that ~0.4s. Both are well within an interactive request budget.

Retrieve-then-rerank — how a checkpoint becomes part of a real ranking

backend/app/engine/algorithmic/recommendation_agent.py

RecommendationAgent.rank_jobs() always computes the cheap algorithmic score (Jaccard exact-match + LEADS_TO partial credit) for every job in the catalog first — the retrieval stage, no model inference involved. Only the top GNN_RERANK_POOL_SIZE (50) candidates by that score get rescored by the GNN and re-sorted; everything outside the pool keeps its algorithmic-only score.

// once a job is in the rerank pool: final_score = exact_score × 0.6 + partial_score × 0.15 + gnn_score × 0.25 // (vs. exact_score × 0.8 + partial_score × 0.2 for the pure-algorithmic path) // gnn_score = average, over the job's still-missing required skills, of the // BEST score_leads_to(owned_skill, missing_skill) across the student's own skills

This is a deliberate systems decision, not just a performance shortcut: scoring every one of ~9,400 jobs with the GNN on each request would be both slow and unnecessary, since the algorithmic pass already discards the overwhelming majority of clearly-irrelevant jobs cheaply. It's also a standard, explainable pattern used in real production recommender systems — narrow a large catalog cheaply, then spend the expensive model only on the candidates worth spending it on.

Why LEADS_TO, not REQUIRES, drives the live rerank

The rerank signal is built entirely from score_leads_to — for each of a job's missing required skills, is there a skill the student already owns that the model thinks plausibly progresses toward it? This deliberately avoids score_requires, since §7 showed the algorithmic baseline beats the GNN outright on that task at this scale — using the weaker-of-the-two-models' signal for live ranking would be indefensible. LEADS_TO, despite its own caveats (synthetic ground truth), is where the model actually demonstrated a genuine, non-tautological learning signal (AUC-ROC 0.679 vs. random-chance 0.500).

match_source — making the claim inspectable, not just asserted

Every job in GET /recommendations/jobs's response carries match_source: "gnn" or "algorithmic". This isn't cosmetic — it's what turns "the GNN is integrated" from a claim about the code into a checkable fact about any specific real response, and it's what a live verification could actually confirm end to end (a real registered student, real skills, a real API call, a real job in the response with "match_source": "gnn").

Wired into EngineOrchestrator.get_job_recommendations(), which passes self.gnn_agent (the cached singleton from §8) into rank_jobs() on every call — the one place in the whole backend where the offline-trained model actually reaches a real user.

Deployment — getting a torch-free API to actually run a torch model

backend/Dockerfile · backend/docker-compose.yml

The backend was deliberately built torch-free (ml/requirements.txt is separate from backend/requirements.txt) so the core API never needs the heavy ML stack just to run its graceful-fallback path. Making the GNN actually live in the deployed container required two real changes, both eventually verified against a running container, not just reasoned about:

  1. Install torch/torch_geometric/scikit-learn in the backend image — the same pinned versions as ml/requirements.txt, so the checkpoint deserializes correctly.
  2. Mount ml/ and backend/data into the container — GNNRecommendationAgent's checkpoint path and graph_build.py's data path are both computed as repo-relative paths assuming ml/ and backend/ are siblings, which is only true inside the container if both are mounted at the paths that assumption expects.
the bug only a real deployment could catch Once deployed, the very first real request crashed: GNNRecommendationAgent's inference path called export_graph.export() (§2) to rebuild the message-passing graph — but that function always writes its result to disk as a side effect meant for its offline CLI use. With ml/ correctly mounted read-only (deliberately, so the running app can't mutate training artifacts), that write failed: RuntimeError: ... Read-only file system — silently violating the exact "never raise" contract §8 describes. Every unit test for that contract (missing checkpoint, corrupt checkpoint, torch absent) had passed the entire build; none of them constructed a read-only-filesystem, production-shaped deployment scenario. Fixed by building the in-memory graph directly (to_hetero_data(build_synthetic_career_graph())) instead of the disk-writing wrapper — inference never actually needed the persisted file. A regression test now asserts export_graph.export is never called by the scoring path at all.

This is the concrete, real example behind a broader lesson stated elsewhere in this project's docs (docs/evaluation-chapter.md §3.1): a fully green test suite is necessary but not sufficient evidence a system works — it took an actual deployment, not a passing test, to find this.
